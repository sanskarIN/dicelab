# Contributing to DiceLab

Thank you for helping improve DiceLab. Contributions should keep the project reliable, accessible, private by default, offline-first, localized through reviewed catalogs, and easy to verify/review.

## Before you start

1. Search existing issues, pull requests, and [`ROADMAP.md`](ROADMAP.md) for related work.
2. Read the [`docs/README.md`](docs/README.md) documentation hub and the closest architecture/policy document for the area you plan to change.
3. For a durable architecture/security/data-contract change, open an issue and plan an ADR before implementation.
4. Keep one pull request focused on one coherent change.
5. Never include credentials, private user data, signing secrets, private backups, configured seeds, private filesystem paths, or production-only endpoints.

## Local setup

See [`docs/setup.md`](docs/setup.md) for platform prerequisites.

```bash
git clone https://github.com/sanskarIN/dicelab.git
cd dicelab
npm ci
npm run dev
```

For the desktop application:

```bash
npm run tauri:dev
```

## Branch and commit style

Use a short descriptive branch name such as `feat/history-filter` or `fix/seed-validation`.

Conventional Commits are preferred:

- `feat: add ...`
- `fix: handle ...`
- `test: cover ...`
- `docs: document ...`
- `refactor: simplify ...`
- `perf: optimize ...`
- `security: harden ...`
- `build: configure ...`
- `ci: verify ...`
- `chore: maintain ...`

Commits should be small and meaningful. Do not create artificial churn merely to increase commit count.

The preferred Git author email for this repository is `sanskarin@outlook.in`.

## Quality checklist

Before opening a pull request, run the relevant checks and record only results you actually observed:

```bash
npm run security:secrets:test
npm run security:secrets
npm run docs:check:test
npm run docs:check
npm run docs:inventory:test
npm run docs:inventory
npm run policy:test
npm run policy:all
npm run test:e2e:infra
npm run version:check:test
npm run version:check
npm run release:verify:test
npm run format
npm run lint
npm run test
npm run build
npm run test:e2e

cd src-tauri
cargo fmt --all -- --check
cargo test --locked
cargo clippy --all-targets --all-features --locked -- -D warnings
```

Not every command is meaningful for every tiny documentation-only change, but dependency/security/architecture boundary changes should run the corresponding policy audits. Release-candidate claims require the fuller evidence documented in [`docs/release.md`](docs/release.md), not merely local unit tests.

Add regression tests for bugs. Add unit tests for business rules. Update docs when behavior, setup, contracts, policy, or release evidence changes. Keep lockfiles generated by package managers and do not hand-edit them to simulate installs.

## Documentation completeness

DiceLab maintains an exhaustive tracked-file reference at [`docs/repository-file-reference.md`](docs/repository-file-reference.md).

When you add, rename, or delete a tracked file:

1. update the exhaustive reference in the same pull request;
2. describe the file's purpose, ownership/boundary, and important relationships;
3. run `npm run docs:inventory`;
4. update the documentation hub or a focused guide when the new file introduces a new concept rather than only a new test case.

`npm run docs:check` validates local Markdown links/anchors; `npm run docs:inventory` validates file coverage. Both are needed because a document can have valid links while still omitting a newly tracked file.

## Accessibility

For UI changes:

- preserve keyboard navigation and visible focus;
- use semantic controls and labels;
- do not communicate status by color alone;
- test reduced-motion behavior;
- keep touch targets comfortable;
- verify light and dark themes;
- preserve readable contrast and scalable text;
- verify modal initial focus, focus containment, dismissal, and focus restoration where applicable;
- review large-list performance changes without sacrificing keyboard or screen-reader access.

See [`docs/accessibility.md`](docs/accessibility.md).

## Localization

DiceLab currently ships reviewed English (`en`) and Hindi (`hi`) interface catalogs. English remains the default.

For user-facing text changes:

- update both `src/i18n/en.ts` and `src/i18n/hi.ts` in the same change unless the work is specifically a translation-review correction;
- preserve the typed `MessageCatalog` shape;
- use catalog functions for dynamic phrases rather than building sentences from fragments;
- keep accessible labels in the catalog when they are user-facing;
- keep built-in preset copy localizable;
- do not translate user-created preset names/descriptions, expressions, seeds, IDs, or persisted/exported machine data;
- use `src/i18n/format.ts` for application-generated locale-sensitive numbers/dates/times;
- update the locale review record when translation policy/coverage changes.

A new locale requires a complete catalog, `LocalePreference` update, explicit `Intl` mapping, persistence/backup/interface/formatting tests, and human review before Settings exposes it.

See [`docs/localization.md`](docs/localization.md) and [`docs/localization/HINDI_REVIEW.md`](docs/localization/HINDI_REVIEW.md).

## Security and privacy

Validate untrusted inputs at boundaries. Avoid remote runtime dependencies unless there is a documented user need and reviewed privacy/security design. Never weaken Tauri capabilities, CSP, offline-network policy, runtime adapters, or native-command allowlists simply to make a feature convenient.

Before native/security changes, review:

- [`SECURITY.md`](SECURITY.md)
- [`docs/capability-policy.md`](docs/capability-policy.md)
- [`docs/tauri-security-policy.md`](docs/tauri-security-policy.md)
- [`docs/offline-network-policy.md`](docs/offline-network-policy.md)
- [`docs/runtime-boundary-policy.md`](docs/runtime-boundary-policy.md)
- [`docs/native-command-contract.md`](docs/native-command-contract.md)
- relevant [`docs/adr/`](docs/adr/) records.

Treat local storage and backup files as potentially malformed. Do not bypass persisted-record validation, backup size limits, duplicate detection, spreadsheet-safe CSV handling, or privacy-safe logging.

Report vulnerabilities according to [`SECURITY.md`](SECURITY.md), not in a public issue.

## Native commands and platform adapters

Production React components should not invoke Tauri directly. Native interactions belong behind focused service adapters, and runtime detection belongs in `src/services/runtime.ts`.

Current product command allowlist:

```text
roll_expression
save_text_export
```

Adding a native command requires Rust input validation, frontend routing tests, command-contract policy updates, capability/CSP review, and documentation/ADR review when it changes the trust boundary.

## Deterministic compatibility

Seeded mode is a cross-runtime compatibility feature. If you change seed hashing, xorshift state transitions, bounded integer conversion, effective-seed construction, or keep/drop behavior that affects results, update the TypeScript and Rust reference-vector tests together and document the compatibility impact.

Never describe seeded mode as cryptographically secure.

## Dependency changes

When `package.json` changes, generate/review the npm lockfile. When `src-tauri/Cargo.toml` changes, regenerate/review `src-tauri/Cargo.lock` using Cargo.

Run:

```bash
npm run policy:lockfiles
```

as an early structural consistency check, but do not treat it as a substitute for `npm ci` or Cargo's locked tests/Clippy. Never hand-edit transitive Cargo lock entries.

See [`docs/lockfile-policy.md`](docs/lockfile-policy.md).

## Pull requests

A good pull request includes:

- a clear problem statement;
- a concise implementation description;
- exact verification commands and observed results;
- real screenshots for visible UI changes when practical;
- accessibility/security/privacy/localization notes when relevant;
- regression tests for changed behavior;
- generated lockfiles when manifests changed;
- documentation/ADR/handoff changes where required;
- no claim that a configured workflow passed unless the run was actually observed.

The repository pull-request template provides the detailed checklist.

## Release-sensitive changes

A change can be merged and still not be release evidence. Candidate evidence must correspond to the exact candidate commit/tag/artifacts.

Use:

- [`docs/release-blockers-current.md`](docs/release-blockers-current.md)
- [`docs/release.md`](docs/release.md)
- [`docs/release-candidate-evidence-template.md`](docs/release-candidate-evidence-template.md)

when working on release preparation.
